# 任务二：Python 版佛山土地交易信息采集技术说明

## 1. 任务理解和网站结构分析

由于已完成任务一，我对任务二有了更清晰的认识。与任务一不同的是，任务二采用 Python 形式实现，但流程与任务一大同小异，均为遍历并抓取 10 页、100 条详情页中的信息。

网站中的元素可以通过 CSS Selector 方式定位，避免了任务一中影刀 RPA 在不同详情页中元素定位不准的问题。该网站我认为比较巧妙的地方，就是通过浏览器检查工具发现：点击详情链接后，需要连续进入两层 iframe 才能定位到最终的数据内容。这个是我在听完课之后，个人觉得最容易忽略的地方。

## 2. 技术方案的选择

我选择了 Playwright。一开始的原因很直接：听完课之后，我按照老师演示的方法试了一遍，因此继续使用 Playwright 完成任务。

在实际使用中，我发现 Playwright 比较适合处理这个网站。它可以模拟浏览器操作，支持使用 CSS Selector 定位元素，也可以处理动态加载、页面跳转和多层 iframe，能够满足本次任务的需要。

## 3. 列表页、onclick 详情链接和两层 iframe 的处理方式

列表页中的历史交易入口、详情按钮和下一页按钮，均采用 CSS Selector 定位。通过观察浏览器检查页面中的元素及其规律，我将需要点击的元素、需要提取的字段和相应的定位方式告诉 Claude Code，由它帮助我编写和完善程序。

详情按钮本身没有普通的 `href` 链接，真实链接位于按钮的 `onclick` 属性中。因此，程序先读取 `onclick` 属性，再从中提取并清理真实的详情页 URL，然后访问该地址。

进入详情页后，程序先定位并进入第一层 iframe，再定位并进入第二层 iframe，最后使用 CSS Selector 提取成交时间、竞得人、交易土地面积、成交地价、地块位置和土地实际用途等字段。

## 4. URL 引号、`--no-headless` 和 GBK 编码等问题及解决办法

为了在较短时间内更方便地完成任务，我将老师开源项目中的部分配置安装到了自己的电脑中。由于老师使用的是 macOS，而我使用的是 Windows，所以其中部分配置需要根据 Windows 环境进行调整。

第一次试运行报错后，我发现从 `onclick` 属性中提取出来的 URL 前面多了一个引号，导致 Playwright 将其判断为无效 URL。我将报错信息交给 ChatGPT 分析，由它生成给 Claude Code 的修改提示词，再把提示词传递给 Claude Code，问题很快得到了解决。

后面运行时，我发现浏览器页面一直在首页和详情页之间切换，看起来像没有进入历史交易页面，但检查导出的结果后发现，程序实际读取的都是历史交易列表中的详情页。这是因为程序需要保留列表页，并逐条进入详情页获取数据，完成后再继续处理下一条记录。

调试过程中还发现，虽然命令中使用了 `--no-headless`，但该参数最初没有被正确传递给 Playwright 的浏览器启动方法，因此看不到浏览器操作过程。修改参数传递逻辑后，程序可以按照需要以可视化模式运行。

另外，有一次运行期间出现报错，原因是 Windows 终端默认使用 GBK 编码，而 Hook 输出中包含 GBK 无法编码的符号。这个问题并不是爬虫主体代码造成的，而是老师的项目配置在 Windows 环境中的兼容性问题。我随后修改了 Hook 的输出内容和编码处理方式，使其能够在 Windows 环境中正常运行。

## 5. Claude Code 在哪些环节提供帮助

Claude Code 主要帮助我完成项目结构搭建、代码编写、网页元素定位逻辑、列表遍历、详情链接提取、两层 iframe 处理、数据导出以及测试代码编写。

在程序出现问题时，我会把运行结果和报错信息提供给 ChatGPT 或 Claude Code，先分析问题，再让 Claude Code 根据修改要求调整代码。代码由 AI 协助完成，但网页结构、字段位置、运行结果以及最终导出的数据仍由我进行检查和确认。

## 6. 如何验证 100 条数据及去重

程序按照任务要求抓取前 10 页，每页 10 条，共导出 100 条记录。数据验证主要采用人工检验的方式：按照列表页进行分组，每 10 条作为一组，检查组内和组间是否存在重复，并结合记录 ID 和详情页链接辅助判断。

同时，我对 Excel 中的数据与网页详情页进行抽查，主要确认成交时间、竞得人、交易土地面积、成交地价、地块位置和土地实际用途等内容是否一致。对于网页中本身没有显示、加载失败或暂时无法确认的数据，不进行主观补填，而是保留为空并继续复核。

最终提交前，我还会再次确认 Excel 中共有 100 条数据，并检查记录 ID 和详情页链接是否存在重复。

## 7. 方案不足和后续改进

目前的不足是电脑访问每一个详情页都比较慢，程序需要逐条打开详情页，并等待页面和两层 iframe 加载完成，因此整体运行时间较长。之后我会研究更加方便和高效的形式，例如进一步分析网站的网络请求，判断是否可以在遵守网站访问要求的前提下直接获取数据。

此外，目前程序比较依赖网页中的 CSS Selector 和 iframe 结构。如果网站后续修改页面结构，相应的定位规则也需要调整。后续还可以继续完善失败重试、断点续爬、自动去重、异常记录和数据完整性检查等功能，使程序运行更加稳定。

## 8. 访问频率和异常处理

程序采用顺序访问方式，没有同时并发打开大量页面。页面加载和翻页时设置了等待时间，并针对网络加载失败增加了重试处理，以减少因网站响应较慢而造成的数据遗漏。

在运行过程中，如果某一条详情页无法正常加载，程序会记录相关信息，避免使用猜测内容替代真实数据。提交结果前，再根据失败记录进行人工复核和必要的补充采集。
